# 0021｜美容检测后台报告管理 V1

## 1. 任务确认卡

- **任务模式**：M2｜标准业务页面。任务在既有 SCRM 客户详情中补齐美容记录列表与三级报告详情，不建设新的产品域或平台基础设施。
- **产品域**：SCRM → 客户 → 客户详情 → 体测美容记录 → 美容记录。
- **业务目标**：完成美容仪厂家报告的数据接入、生产存储口径、奥本客户关联和后台只读查看，在与体测记录一致的客户上下文和抽屉体系中查询当前客户的美容检测历史并查看奥本后台美容报告。
- **修改范围**：既有客户详情内的美容记录二级 Tab、美容记录列表、单一“查看”操作、三级美容详情 Drawer、美容数据到 SCRM 的只读适配、真实 Story 与测试。
- **明确不做**：独立后台菜单、设备管理、设备与 IP 映射/监控、所属员工/门店、厂家图片下载或缓存、后台业务写操作、本原型内建设真实后端/API/数据库/LocalStorage、新依赖、体测业务或客户详情结构重构。
- **业务规则**：只展示美容检测 JSON 已提供且已经过脱敏确认的字段；客户、报告和厂家身份必须分离；列表与详情始终绑定当前客户和当前所选报告；检测设备 IP 只作为当前报告的只读展示字段，不建设设备与 IP 映射或监控能力。
- **UI 等级**：B 级。页面层级、抽屉关系、Tab、列表与详情信息布局以正式参考图为主要视觉基准；不自行升级为 C 级逐像素验收。
- **验收标准**：从 SCRM 客户列表真实链路进入客户详情，在美容记录中查看历史并打开对应三级详情；关闭三级 Drawer 后仍保留当前客户、美容 Tab 与列表状态；多记录不串数据，既有体测记录及体测详情无回归。

## 6. Cycle A｜美容记录列表 + 报告详情

### 6.1 美容记录列表

将当前美容空状态替换为当前客户的美容检测历史列表。字段严格为 7 列，顺序固定：

1. 检测时间。
2. 综合得分。
3. 等级。
4. 肤质类型。
5. 肤质标签。
6. 检测设备 IP。
7. 操作。

操作列只包含一个固定文字入口：`查看`。点击后打开当前行对应的美容检测报告详情三级 Drawer。不得使用下拉菜单、合并入口或新增其他操作。

列表规则：

- 只显示当前 `customerId` 关联的记录，按检测时间倒序。
- 空值统一显示 `--`；不得用其他记录或默认文案补值。
- 综合得分、等级、肤质类型、肤质标签沿用正式美容标准模型及 adapter 的展示口径，组件不重新计算等级。
- 肤质标签保持厂家返回顺序，以当前后台密度展示，不自行拆分或重命名。
- 检测设备 IP 使用 shared 标准模型或 SCRM view model 中已确认的只读字段；缺失时显示 `--`，不得由设备序列号、设备 ID 或其他字段推断。
- 有数据时不显示空态；无当前客户记录时继续显示统一空态“暂无美容记录”。
- 不新增筛选、排序、分页、导出、批量操作或刷新能力，除非参考图及当前通用行为已有明确要求并经任务单修订确认。

### 6.2 操作列

操作列直接显示一个文字入口：`查看`。点击该入口只打开该行对应的美容检测报告详情三级 Drawer，不提供其他操作或记录链接。

## 7. 美容检测报告详情三级 Drawer

### 7.1 Drawer 基线

- 标题：`美容检测报告详情`。
- 右侧内层三级 Drawer，保留外层客户详情和美容列表上下文。
- Header 只保留固定标题与既有关闭入口。
- 标题下不得展示厂家报告标题、厂家报告名称或任何厂家原始信息。
- Drawer 正文独立纵向滚动，Header/关闭入口稳定可见；不得让整个 SCRM 页面承担报告滚动。
- 切换/关闭不得修改客户身份、列表数据或体测记录状态。

### 7.2 基础信息

基础信息只展示：

1. 性别。
2. 年龄。
3. 综合得分。
4. 等级。
5. 肤质类型。
6. 肤质标签。
7. 检测时间。
8. 检测设备 IP。

约束：

- 除后台检测设备 IP 外，其他美容业务字段复用正式美容模型的统一语义与 formatter。
- 不展示姓名、手机号、头像、厂家报告名称、厂家客户 ID、奥本客户 ID、报告 ID、任务 ID、其他设备标识、原始链接或厂家图片信息。
- 不因后台展示需要修改移动端字段合同；后台专用元数据应通过清晰的 admin view model/adapter 边界承载。
- 性别、年龄、数值、等级、时间和空值均沿用已确认 adapter/formatter，不在 JSX 内解释厂家原始类型或重算等级。

### 7.3 综合建议

- 展示厂家 `ComprehensiveProposal[]` 中已确认的综合建议内容，保持厂家返回标题、文本和顺序。
- 可按数据中已有的“问题分析”“护理建议”等标题分段，但不得 AI 总结、改写、合并或补充内容。
- 某段无数据时不渲染空标题和空容器；全部无数据时使用统一空态，不生成示例结论。
- 不展示厂家配图、图片 URL 或其他富媒体。

### 7.4 单项报告

按照厂家报告配置/结果中的真实顺序动态展示有效项目，不按分数排序，也不以硬编码项目白名单丢弃厂家新增的有效项目。V1 只保证已确认接口字段的完整映射，每项当前确认字段为：

- 名称。
- 得分。
- 等级。
- 问题分析。
- 日常护理建议。

当前已知项目名称包括油脂、毛孔、黑头、浅层色素、混合斑、痤疮、屏障、卟啉、深层色素、棕色色素、紫外线斑、敏感红素图、敏感热力图、皱纹、粗糙度、胶原。该清单只作为当前报告验收基准，不是厂家永久固定白名单；必须以脱敏数据中的原文为准，不把“卟啉”改为“叶啉”，也不把“敏感红素图”改为其他近似名称。

厂家未来新增、但结构尚未被 V1 确认的单项可以展示项目名称；V1 不要求自动解析其未知字段，不要求自动生成问题分析或护理建议，也不得为了兼容未来未知结构设计通用字段引擎。只有名称、得分、等级、问题分析、日常护理建议这五类已确认字段进入当前映射合同。

展开规则：

- 默认收起；点击当前项展开，再次点击收起。
- 允许多项同时展开，不强制手风琴互斥。
- `问题分析` 只消费当前项映射后的 `problemAnalysis`。
- `日常护理建议` 只消费当前项映射后的 `careAdvice`，兼容厂家标题“日常护理建议”与“护理建议”统一归一化后的业务字段。
- 保持厂家原文和数组顺序，不 AI 改写、不补科普、不生成建议。
- 某一区块为空时不渲染对应标题或空容器；两者均为空时保留项目头，不生成假内容。
- 不展示检测图片、三脸图、Area、Rate、单项 Count、Image 字段或厂家富媒体。

## 8. 数据模型与依赖边界

### 8.1 共享策略

- 0021 必须复用实施基线中正式发布的美容标准模型、纯 adapter、selectors 和脱敏稳定 Mock，遵循 `shared → products` 单向依赖。
- SCRM 可以创建后台专用的列表/详情 view model，但不得复制第二套 `BeautyReport`、单项 Content 解析、等级计算或动态排序规则。
- `src/shared/beauty-assessment/` 不得依赖 SCRM 组件、Ant Design、客户 Drawer 或 Story。
- 不得合并 `BodyAssessmentReport` 与 `BeautyReport`，不得让美容记录走体测 adapter。

### 8.2 身份与记录关联

- `customerId` 只表示奥本客户 ID，用于关联当前 SCRM 客户。
- `vendorCustomerId`、`vendorReportId`、`vendorTaskId` 如存在必须保持厂家身份语义，不与 `customerId` 互换。
- 列表行和详情 Drawer 必须使用同一个稳定美容记录 ID 选择同一条记录，不维护第二套“当前详情”数据。
- 当前客户没有关联记录时为空态；不得把其他客户的报告作为兜底。

### 8.3 厂家字段与类型归一化

- 厂家 `Status / FaceType / Score / Level / Age / Count` 等字段可能为字符串，必须先由 adapter 做类型归一化，再进行过滤、排序或展示。
- 单项先归一化，再按已确认有效规则筛选；React 组件不得直接解析 `ResultDetail[].Content`。
- 检测设备 IP 必须来自实施前确认的 shared 标准字段或 SCRM view model 映射；若脱敏 fixture 缺少该字段，按空值处理，不猜测、不造值。
- 完整厂家 raw JSON、姓名、手机号、头像、真实客户 ID 对应关系、Token、图片地址和设备敏感信息不得提交到原型仓库；生产原始快照按第 10 节受控保存，不得暴露给页面。

### 8.4 原型数据

- 使用少量稳定、脱敏 Mock 覆盖：当前客户多条美容历史、另一客户隔离、空记录、不同检测设备 IP、单项有/无 Content。
- Mock 必须经正式 adapter 进入统一模型，不能直接构造只适配 UI 的另一套结构。
- 刷新允许恢复初始 Mock；不使用 LocalStorage、后端、数据库或新 Provider/store。
- 若 0020 已有符合这些条件的数据源，直接复用，不复制 fixture。

## 9. 数据字段定义

V1 所有列表和详情展示字段必须按下表追溯来源。表中的“存储”指生产系统的数据接入与持久化要求；当前 HTML 原型只用脱敏 fixture 验证 adapter、客户关联和页面展示，不在本仓库实现真实数据库。

| 字段名称 | 业务字段/来源 | 生产 V1 是否存储 | 页面是否展示 | 规则 |
| --- | --- | --- | --- | --- |
| 厂家报告 ID | 厂家报告列表 `reportId` → `vendorReportId` | 是 | 否 | 当前记录唯一关联键之一，不等同于 `vendorTaskId` |
| 厂家任务 ID | 厂家结果 `TaskId` → `vendorTaskId` | 是 | 否 | 与厂家报告 ID 分开保存，除非厂家正式确认两者等价 |
| 厂家客户 ID | 厂家客户/报告 `CustomerId` → `vendorCustomerId` | 是 | 否 | 仅用于厂家侧追溯，不得替代奥本客户 ID |
| 奥本客户 ID | 奥本客户系统 `customerId` | 是 | 否 | 当前 SCRM 客户与美容记录的正式关联键 |
| 检测时间 | 厂家报告 `ServerCreateTime` | 是 | 是 | 由统一 formatter 展示，不在页面自行转换时区 |
| 性别 | 厂家报告 `Customer.Sex` | 是 | 仅详情 | 使用已确认枚举映射，未知显示 `--` |
| 年龄 | 厂家报告 `Customer.Age` | 是 | 仅详情 | adapter 先做类型归一化，缺失显示 `--` |
| 综合得分 | 厂家报告 `Score` | 是 | 是 | 列表与详情共用同一标准字段 |
| 综合等级 | 根据厂家已确认 Score 规则在 adapter 中转换为 `scoreLevel` | 是 | 是 | 页面禁止重复计算等级 |
| 肤质类型 | 厂家报告 `LevelName` | 是 | 是 | 保留厂家原文 |
| 肤质标签 | 厂家报告 `LevelLabel[]` | 是 | 是 | 保留厂家顺序，不建设奥本客户标签体系 |
| 检测设备 IP | shared 标准模型或经确认的 SCRM view model 字段 | 根据接口确认 | 是 | 只读展示；缺失显示 `--`，不维护设备与 IP 映射 |
| 综合建议 | 厂家报告 `ComprehensiveProposal[]` | 是 | 仅详情 | 保留厂家标题、正文与顺序，不 AI 改写 |
| 单项报告 | 厂家报告 `ResultDetail[]` 及报告配置顺序 | 是 | 仅详情 | 以动态集合/JSON 结构保存，不拆成固定项目列 |
| 单项问题分析 | `ResultDetail[].Content` 中标题为“问题分析”的内容 | 是 | 展开后展示 | adapter 归一化，保留厂家原文与顺序 |
| 单项护理建议 | `ResultDetail[].Content` 中“日常护理建议”或“护理建议” | 是 | 展开后展示 | 统一映射到 `careAdvice`，不生成新文案 |
| 厂家原始报告 JSON | 厂家报告原始响应 | 是 | 否 | 生产侧按第 10 节保存；不得将真实原始数据提交到原型仓库 |

除表中字段外，开发不得自行推测来源、持久化口径或展示范围。检测设备 IP 的真实接口路径必须在实施前确认，不得从相似字段推导。

## 10. 厂家原始数据保存

生产 V1 明确保存厂家返回的原始报告 JSON，用于追溯厂家字段、重新适配和核对历史报告；同时保存第 9 节中页面需要的标准化字段及奥本客户关联。数据流固定为：

```text
厂家原始报告数据
→ 服务端受控保存原始快照
→ adapter 转换
→ 标准美容报告/后台展示模型
→ 页面只读展示
```

约束：

- 页面和 SCRM 业务组件禁止直接读取厂家原始 JSON。
- adapter 只负责字段转换、有效数据过滤、原始类型归一化、格式统一和已确认 Content 映射。
- 厂家字段路径变化应收敛在 adapter/接入层，不把原始字段判断散落到 React JSX。
- 原始快照与标准化模型必须保留稳定 `vendorReportId`，并通过奥本 `customerId` 建立客户关联；不得按手机号、姓名或“最新一条”临时关联。
- V1 原型只需保留 `vendorReportId` 的字段映射和记录关联能力。生产接入的幂等、重复报告识别与写入策略由服务端接入实现确认，不作为 0021 页面开发阻塞，也不得由前端页面自行实现。
- 生产环境原始数据的访问权限、保存期限、加密与脱敏必须遵循现有数据安全规范；这些基础设施不在当前 HTML 原型仓库实现。
- 原型仓库不得提交完整厂家 raw JSON、PII、头像/人脸、图片地址、真实客户对应关系或 Token；测试只使用最小脱敏 fixture。

## 11. 后台查询展示边界

0021 只负责 SCRM 客户详情内美容检测结果的沉淀与查看，提供“美容记录列表 → 查看 → 当前记录三级 Drawer”的后台查询展示链路。

## 12. 单项检测展示规则

单项检测集合来自厂家 `ResultDetail[]`，页面按厂家报告配置/结果顺序动态生成，不以数据库固定列或 JSX 固定列表作为展示来源。

禁止把油脂、毛孔、黑头、皱纹等项目设计为独立固定字段，例如 `oil`、`pore`、`blackhead`、`wrinkle`；禁止将当前 16 项名单作为数据库 schema 或页面渲染白名单。生产存储应保留动态项目集合、稳定厂家项目标识/类型和第 7.4 节已确认的单项字段。

厂家新增或减少项目时：

- 若新项目继续使用 V1 已确认结构，adapter 可直接产生标准单项，页面无需修改代码即可按数据顺序展示。
- 若厂家改变字段结构，只修改 adapter/接入层；页面仍消费标准单项模型。
- 对结构尚未确认的未来项目，继续遵守第 7.4 节边界：可保留项目名称，但不解析未知字段，也不生成问题分析或护理建议。
